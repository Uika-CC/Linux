

# Linux 运维笔记：systemd 服务管理与故障排查

## 一、systemd 是什么

systemd 是 Linux 中重要的系统与服务管理组件，通常作为 PID 1 运行，负责系统初始化以及服务、挂载点等资源的管理。

### 1. 什么是 Unit

Unit 是 systemd 管理的对象。不同类型的 Unit 用于管理不同的系统资源或任务。

| Unit 类型    | 作用                                          |
| ------------ | --------------------------------------------- |
| `.service`   | 管理服务或进程                                |
| `.timer`     | 定时触发任务                                  |
| `.socket`    | 管理套接字，可配合服务实现按需启动            |
| `.mount`     | 管理文件系统挂载                              |
| `.target`    | 将多个 Unit 组织成一个目标                    |
| `.automount` | 管理自动挂载                                  |
| `.path`      | 根据文件或目录变化触发任务                    |
| `.device`    | 表示 systemd 可识别的设备                     |
| `.swap`      | 管理交换空间                                  |
| `.slice`     | 对进程进行资源组织与管理                      |
| `.scope`     | 管理由其他方式创建、纳入 systemd 管理的进程组 |

**注意：** Unit 不等于 Unit 文件。Unit 文件是描述 Unit 配置的一种方式；运行时也可能存在动态生成的 Unit。

### 2. 常见 Unit 文件目录

- `/usr/lib/systemd/system/`：软件包提供的 Unit 文件，常见于 RHEL 系列发行版。
- `/etc/systemd/system/`：管理员创建或覆盖的配置，也常用于自定义服务。
- `/run/systemd/system/`：运行期间生成的 Unit 配置，通常重启后不保留。

排查某个服务实际使用哪个 Unit 文件：

```
systemctl cat sshd
systemctl show sshd -p FragmentPath
```

### 3. Unit 文件的基本结构

```
[Unit]
Description=Heartbeat Test Service
After=multi-user.target

[Service]
Type=simple
ExecStart=/usr/local/libexec/heartbeat.sh
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

#### `[Unit]`：描述与依赖关系

- `Description=`：服务的说明。
- `After=`：规定启动顺序，不代表自动启动所写的依赖。
- `Wants=`：建立较弱的依赖关系。
- `Requires=`：建立较强的依赖关系。

#### `[Service]`：服务如何运行

- `Type=simple`：默认类型之一。systemd 启动指定进程后，通常就将服务视为已启动，不代表业务功能一定正常。
- `ExecStart=`：启动服务时执行的命令。
- `Restart=on-failure`：符合失败条件时尝试重新启动服务。
- `User=`：指定服务运行用户。
- `WorkingDirectory=`：指定工作目录。
- `ExecStop=`：指定停止服务时执行的命令。

#### `[Install]`：配置启用关系

- `WantedBy=multi-user.target`：执行 `enable` 时，用于建立相应的依赖关系链接。

`WantedBy=` 不是服务启动命令。服务是否正在运行，与是否设置为开机启动，是两个不同的问题。

### 4. 服务的常见管理命令

```
# 查看服务状态
systemctl status heartbeat

# 启动、停止、重启
sudo systemctl start heartbeat
sudo systemctl stop heartbeat
sudo systemctl restart heartbeat

# 设置开机启动或取消
sudo systemctl enable heartbeat
sudo systemctl disable heartbeat

# 立即启动，并设置开机启动
sudo systemctl enable --now heartbeat

# 查看服务是否设置为开机启动
systemctl is-enabled heartbeat

# 查看服务是否正在运行
systemctl is-active heartbeat
```

**记忆要点：**

- `start`：现在启动。
- `stop`：现在停止。
- `restart`：重新启动。
- `enable`：配置开机启动关系。
- `disable`：取消开机启动关系。
- `enable --now`：配置开机启动，并立即启动。

`disable` 通常不会自动停止当前正在运行的服务。

### 5. 修改 Unit 文件后怎么办

```
# 重新读取 Unit 配置
sudo systemctl daemon-reload

# 重新启动服务，让新的服务配置生效
sudo systemctl restart heartbeat

# 查看状态
systemctl status heartbeat
```

`daemon-reload` 只负责让 systemd 重新读取 Unit 配置，不等于重启服务，也不能修复脚本自身的语法错误。

如果服务因为连续失败进入失败状态，可在修复问题后执行：

```
sudo systemctl reset-failed heartbeat
sudo systemctl start heartbeat
```

`reset-failed` 用于清除失败状态和相关的启动频率限制记录，不负责修复根本原因。

## 二、systemd 服务故障排查

### 1. 先区分故障类型

遇到服务异常，先判断属于哪一类：

1. **服务无法启动**：进程没有成功运行。
2. **服务启动后退出**：进程运行一段时间后崩溃或自行结束。
3. **服务显示运行，但功能异常**：进程存在，但程序没有正常工作。
4. **服务运行正常，但外部无法访问**：可能涉及监听地址、端口、防火墙、SELinux 或网络配置。

不同现象对应的排查方向不同，不必每次都从头检查所有层次。

### 2. 第一层：查看状态与日志

```
# 查看状态、退出码及最近日志
systemctl status heartbeat --no-pager -l

# 查看本次开机以来的服务日志
sudo journalctl -u heartbeat -b --no-pager

# 查看最近 50 条服务日志
sudo journalctl -u heartbeat -n 50 --no-pager

# 实时跟踪服务日志
sudo journalctl -u heartbeat -f

# 查看本次开机以来的错误级别日志
sudo journalctl -u heartbeat -p err -b --no-pager
```

重点观察：

- 服务当前是 `active`、`inactive` 还是 `failed`。
- 是否出现 `Failed`、`Permission denied`、`No such file or directory` 等信息。
- 是否出现 `status=203/EXEC` 等退出状态。
- 日志中指出的文件路径、进程、时间和具体错误是什么。

**原则：先收集证据，再决定下一步检查什么。**

### 3. 第二层：检查 Unit 配置

```
# 查看实际加载的配置内容
systemctl cat heartbeat

# 查看主 Unit 文件路径
systemctl show heartbeat -p FragmentPath

# 查看 systemd 解析出的启动命令
systemctl show heartbeat -p ExecStart

# 检查 Unit 文件语法
sudo systemd-analyze verify /etc/systemd/system/heartbeat.service
```

检查内容：

- Unit 文件路径是否正确。
- `[Unit]`、`[Service]`、`[Install]` 等节名称是否拼写正确。
- `ExecStart=` 是否指向真实存在的文件。
- `User=`、`WorkingDirectory=` 等配置是否合理。
- 依赖关系与启动顺序是否正确。

注意：`systemd-analyze verify` 可以帮助发现部分 Unit 配置问题，但不能证明应用程序本身一定正常。

### 4. 第三层：检查脚本或程序本身

如果服务启动的是 Shell 脚本，可检查：

```
# 查看文件内容及行号
nl -ba /usr/local/libexec/heartbeat.sh

# 查看权限与属主
ls -l /usr/local/libexec/heartbeat.sh

# 查看文件类型
file /usr/local/libexec/heartbeat.sh

# 检查脚本语法
bash -n /usr/local/libexec/heartbeat.sh
```

重点检查：

- Shebang 是否正确，例如 `#!/bin/bash`。
- 文件是否具有执行权限。
- `ExecStart=` 路径是否正确。
- 脚本是否有语法错误。
- 运行用户是否有权限访问脚本及其需要的文件、目录。
- 脚本依赖的命令是否存在，运行环境是否满足要求。

如果怀疑父目录权限：

```
namei -l /usr/local/libexec/heartbeat.sh
```

这可以逐级检查路径上的目录和文件权限。即使脚本本身可执行，父目录缺少必要的搜索权限也可能导致执行失败。

### 5. 第四层：结合错误检查 SELinux

传统 Linux 文件权限主要通过用户、组和读写执行权限进行控制；SELinux 则在此基础上实施额外的强制访问控制。

常用命令：

```
# 查看 SELinux 模式
getenforce
sestatus

# 查看文件的 SELinux 安全上下文
ls -lZ /usr/local/libexec/heartbeat.sh

# 查看进程的安全上下文
ps -eZ

# 查看最近的 AVC 拒绝记录
sudo ausearch -m AVC -ts recent
```

排查思路：

1. 先确认是否存在 SELinux 拒绝记录。

2. 查看被拒绝的进程、目标文件、操作类型和安全上下文。

3. 判断文件标签是否与其实际用途相符。

4. 如果标签不正确，可根据系统默认策略使用 `restorecon` 恢复：

   sudo restorecon -v /usr/local/libexec/heartbeat.sh

不要因为服务启动失败就直接关闭 SELinux。应根据审计记录确认问题，并修复标签或策略。

### 6. 第五层：服务进程、端口与网络

如果服务已经运行，但功能异常或外部无法访问，可继续检查：

```
# 查看进程
ps -ef | grep '[h]eartbeat'

# 查看监听端口
sudo ss -lntup

# 查看防火墙规则
sudo firewall-cmd --list-all

# 查看当前 IP 地址
ip addr

# 查看路由
ip route
```

对于 Web 服务等网络程序，还要检查：

- 程序是否监听正确的 IP 地址与端口。
- 本机访问是否正常。
- 防火墙及云平台安全组是否允许对应流量。
- 服务是否依赖 DNS、数据库或其他网络服务。

**注意：** `heartbeat.sh` 这个实验脚本只写本地文件，并不监听网络端口，因此不需要为了它专门排查防火墙或网络。排障范围要与实际故障相匹配。

## 三、常见错误的定位方向

| 现象或错误                     | 优先检查方向                                             |
| ------------------------------ | -------------------------------------------------------- |
| `203/EXEC`                     | `ExecStart` 路径、文件权限、Shebang、父目录权限、SELinux |
| `No such file or directory`    | 文件路径、解释器路径、脚本格式、依赖文件                 |
| `Permission denied`            | 用户权限、目录权限、执行权限、SELinux                    |
| `Unit not found`               | Unit 名称、文件路径、`daemon-reload`                     |
| `bad-setting` 或 Unit 配置错误 | Unit 文件语法、选项名称、配置值                          |
| `Address already in use`       | 端口占用、重复进程、监听配置                             |
| 服务运行但访问失败             | 监听地址、端口、防火墙、安全组、网络、应用日志           |
| 服务启动后很快退出             | 应用日志、程序退出码、运行用户、依赖与环境               |

错误码只能帮助缩小范围，不能单独证明根因。以状态输出、日志和实际检查结果为准。

## 四、一次完整的排障流程

遇到服务问题，可以按下面的流程执行：

1. **明确现象**：无法启动、启动后退出，还是运行中但功能异常？
2. **查看状态和日志**：`systemctl status`、`journalctl`。
3. **依据证据选择检查层次**：Unit、程序、文件权限、依赖、SELinux 或网络。
4. **一次验证一个假设**：先定位，再修改，避免同时改变多个配置。
5. **验证修复结果**：确认服务状态、日志，以及实际功能是否恢复。
6. **记录根因与修复方法**：以后遇到同类问题，可以更快定位。

推荐优先记住的排障组合：

```
systemctl status 服务名 --no-pager -l
sudo journalctl -u 服务名 -b --no-pager
systemctl cat 服务名
systemctl show 服务名 -p FragmentPath -p ExecStart
sudo systemd-analyze verify /etc/systemd/system/服务名.service
```

根据证据，再检查程序文件、权限、SELinux 或网络。

## 五、Heartbeat 实验复盘

本次实验的核心不是“成功写出一个 Unit 文件”，而是完成了一次多层故障定位：

- 修正 Shell 脚本本身的问题。
- 发现并修正 Unit 节名称的大小写错误。
- 通过 `systemctl status` 和 `journalctl` 观察启动失败。
- 结合 SELinux 审计信息，定位执行操作被拒绝的问题。
- 将脚本放到合适的位置，确认安全上下文与默认策略相符。
- 重新加载 Unit、清理失败状态并启动服务。
- 最终确认服务进程持续运行。

这次建立的排障思路可以迁移到 Nginx、数据库、Web 应用和其他 systemd 服务上。

**核心原则：不要只看服务“起没起来”，要理解 systemd 如何启动它、进程为什么失败，以及系统的权限和安全策略如何影响它。**
